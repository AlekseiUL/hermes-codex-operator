# RFC-0001: Reliable Hermes to Codex task lifecycle

**Status:** Accepted historical `v0.0.1` baseline
**Audience:** maintainers, adapter authors, and reviewers
**Protocol version:** `1`

This RFC records the first-release lifecycle. The additive observation,
continuation, shared-queue, dispatch-kind, and recovery rules in the `v0.1.0`
candidate are specified by [RFC-0002](RFC-0002.md). The public WorkContract
schema remains version `1`; the journal schema is internal and versioned
separately.

## 1. Problem

Calling Codex is easy. Reliably owning the whole task lifecycle is not. A
caller must know which workspace, thread, turn, and result belong together;
must not duplicate a turn after a lost response; and must distinguish a model's
claim of success from verified workspace evidence.

The first MVP provides a small transactional operator between a conversational
technical partner and Codex App Server. It does not replace either system.

## 2. Product sentence

Hermes prepares the engineering brief, Codex executes it, and Operator
enforces stable identity, conservative recovery, authoritative readback, and
evidence-gated delivery: either a verified result or an explicit non-success
state for one logical task.

## 3. Trust boundaries

| Boundary | Trusted for | Not trusted for |
|---|---|---|
| Human/caller | intent and explicit permission | schema correctness |
| Hermes adapter | producing a task contract | proof that code is correct |
| Operator core | state transitions and local journal | OS-level sandboxing |
| Codex App Server | authoritative thread/turn state | product acceptance by itself |
| Codex model output | useful implementation report | evidence of changed files/tests |
| Workspace | project inputs | absence of symlink/path escape |
| Verification process | exit code and bounded output | safe shell parsing; no shell is used |

Operator is not a security boundary. It composes Codex sandboxing with its own
validation and evidence checks.

## 4. Logical identities

- `task_id`: stable product task; maps to one workspace and one Codex thread.
- `operation_id`: one user instruction within a task; maps to at most one Codex
  turn.
- `prompt_sha256`: detects reuse of an operation ID with different content.
- `thread_id`: authoritative Codex thread identity, stored locally.
- `turn_id`: authoritative Codex turn identity, stored locally.

A repeated `operation_id` with the same digest returns existing state. A repeat
with a different digest is an idempotency conflict.

## 5. State machine

```text
QUEUED
  -> STARTING_THREAD -> READY
  -> DISPATCHING -> RUNNING
  -> TURN_COMPLETED -> VERIFYING -> VERIFIED

Any active state may become:
  FAILED | CANCELLED | TIMED_OUT | UNKNOWN

Verification may become:
  VERIFICATION_FAILED | SCOPE_VIOLATION
```

`TURN_COMPLETED` is not equivalent to `VERIFIED`.

Every immutable terminal state (`VERIFIED`, `FAILED`, `CANCELLED`,
`VERIFICATION_FAILED`, or `SCOPE_VIOLATION`) and its receipt are committed in
one SQLite transaction. The ordinary transition API cannot create one of these
states without its receipt.

`UNKNOWN` means Operator cannot prove whether a side effect occurred. Automatic
resubmission from `UNKNOWN` is forbidden. Recovery must reconcile the exact
thread/turn or require an explicit human decision.

## 6. Task contract

The version 1 request contains:

```json
{
  "schema_version": "1",
  "task_id": "demo-task",
  "operation_id": "demo-task-001",
  "workspace": "/absolute/path/to/workspace",
  "prompt": "Implement the requested behavior and run the checks.",
  "allowed_change_globs": ["src/**", "tests/**"],
  "verification": [["python3", "-m", "unittest", "discover", "-s", "tests"]],
  "timeout_seconds": 900
}
```

Optional model and reasoning settings are caller configuration, never personal
or hard-coded repository defaults.

Unknown top-level fields are rejected in protocol version 1. Inputs have bounded
length, count, and output limits.

The raw contract remains caller-owned private recovery input. It must be
retained unchanged outside Git and outside the target workspace until the
operation is terminal; the journal intentionally stores its prompt digest
rather than the prompt itself.

## 7. Workspace policy

Before dispatch, Operator:

1. resolves the workspace canonically;
2. confirms it is a directory under one configured allowed root;
3. rejects escaping symlinks and path traversal;
4. captures a bounded baseline manifest;
5. records only relative changed paths and content digests in evidence.

After completion it captures a second manifest. Protocol v1 requires at least
one allowed-change glob, and every changed path must match one of them.

## 8. App Server protocol

The adapter uses documented v2 methods through Codex's experimental App Server
executable. Compatibility is qualified per exact CLI version:

1. spawn `codex app-server --listen stdio://`;
2. send `initialize`, then `initialized`;
3. call `thread/start` for a new task or `thread/resume` for an existing task;
4. persist the returned `thread.id` before starting a turn;
5. mark `DISPATCHING` durably before `turn/start` leaves the process;
6. persist `turn.id` as soon as the response arrives;
7. wait for the matching `turn/completed` notification;
8. call `thread/read` with `includeTurns=true` and extract the exact turn;
9. treat that readback, not streamed deltas, as authoritative.

The first MVP runs one local App Server process per operation. Durable thread
identity allows a later process to resume the same task. RFC-0002 adds one
explicit managed-daemon direct Unix-socket path for active-task queueing; it
does not change this baseline behavior for ordinary submissions.

## 9. Dispatch and recovery semantics

The App Server protocol does not currently give the client a general
idempotency key for `turn/start`. Therefore the portable core promises
**at-most-once automatic dispatch**, not magical exactly-once execution.

- Crash before `DISPATCHING`: the operation may be safely attempted.
- Crash after `turn_id` is persisted: reconcile the exact turn.
- Lost response after dispatch but before `turn_id` persistence: record
  `UNKNOWN`; never resend automatically.
- Timeout while a turn may still be running: record `TIMED_OUT`; later status
  may reconcile the exact turn, but does not create a second turn.

## 10. Permissions and approvals

The local MVP defaults to `workspace-write` and no automatic sandbox escape.
If Codex needs a permission the current policy does not grant, the operation
fails closed. Interactive approval needs a future protocol version; v0.0.1
never silently broadens permissions.

The adapter accepts Codex's documented special temporary roots (`tmpdir` and
`slash_tmp`) as runtime writes. It rejects ordinary writable roots outside the
selected workspace and unexpected network access. Operator is not an OS-level
sandbox and does not claim temporary directories are part of workspace
evidence.

## 11. Verification and receipt

Verification commands are arrays of argv strings and run with `shell=false`.
Each result records command digest, exit code, duration, and bounded/redacted
output digest. Raw output is not part of the default public receipt.

Those commands are trusted caller-selected host processes, not Codex-sandboxed
commands. They run with the operator user's OS permissions. Workspace diffing
is post-hoc evidence and cannot prevent writes outside the workspace.

The default receipt contains:

- schema version, task/operation IDs and terminal status;
- prompt, workspace, thread, turn, and authoritative-result digests rather
  than raw private values;
- relative changed paths and their digests;
- verification exit codes and output digests;
- timestamps and a machine-readable failure code.

## 12. Hermes boundary

Hermes owns conversation, Telegram delivery, technical decomposition, and user
clarification. The Hermes adapter only converts a validated WorkBrief into the
versioned Operator contract and converts a receipt into a user-facing summary.

No Telegram token, chat ID, agent profile, Kanban route, or private team context
belongs in this repository.

## 13. Desktop boundary

Creating a saved Local Project and a visibly assigned task in Codex Desktop is
valuable but platform- and version-sensitive. It is an optional Phase 2 macOS
adapter. The portable core must remain useful with App Server alone.

The Desktop adapter may read supported state and use documented deep links or
accessibility actions, but must be version-gated, opt-in, fail closed, and never
write private Codex databases directly.

## 14. Non-goals

- general multi-agent orchestration;
- Telegram or other messaging gateway;
- Kanban and background scheduling;
- arbitrary remote shell execution;
- automatic commits, pushes, PRs, deployment, or publishing;
- memory/vector database;
- web UI, telemetry, or analytics;
- support for multiple coding harnesses in the first MVP.

## 15. MVP acceptance gate

The MVP is acceptable only when:

1. duplicate operation delivery never creates a second adapter dispatch;
2. conflicting reuse of an operation ID is rejected;
3. crash/response-loss ambiguity becomes `UNKNOWN`, not a retry;
4. restart can reconcile a persisted thread and turn;
5. completion is followed by authoritative readback;
6. changed-path and verification failures cannot produce `VERIFIED`;
7. all tests pass in a synthetic temporary workspace;
8. source, Git history, and release archive contain no secret, PII, private
   path, runtime state, or private-team binding;
9. a clean environment can run tests without any private infrastructure.
